# Build the tinker sidebar revamp

> Version: v0.100
> Generated by the product-spec skill.

Build the v1 of the revamped tinker sidebar from this prompt. The founder has worked through a guided interview that distilled the idea into the structure below; this is the imperative form a build agent executes against.

The revamp turns the existing left sidebar (brand at top, flat seed list in the middle, Account block at the bottom) into a **mirror of what the founder is writing about** — a short list of named themes lifted verbatim from their own seed drafts, grouped underneath each label. The seed list goes away; the themes list takes its place. The brand and Account skeleton stay.

## Anti-patterns — do not repeat

- **Don't invent a new sidebar component alongside the existing `.sidebar`.** This is a refactor in place. The current `<aside class="sidebar" id="sidebar">` in `src/renderer/index.html` stays; the `#home-list` slot is what changes. A second sidebar bolted alongside the first is the failure mode.
- **Don't introduce new fonts, new colors, new button visuals, new icon libraries, or a CSS framework.** The visual canon is `src/renderer/styles.css` + `src/renderer/design-tokens.css` + `src/renderer/tokens/rainbow-web.json`. Reuse `.sidebar__account-item` style for theme rows; reuse the warm-cream surface and Plus Jakarta Sans / Inter that the rest of tinker uses. If a visual decision isn't already made in those files, stop and ask the founder before inventing.
- **Don't author theme labels.** Theme labels are verbatim phrases lifted from the founder's own writing — a fragment of a sentence they actually wrote. The AI clusters, ranks, and selects; it does not paraphrase, prettify, summarize, or compose. A label like "your career stuff" or "growth in family relationships" is a bug; a label like "the barber shop" or "hop tinctures at 7am" — pulled verbatim from a seed — is correct.
- **Don't ship judgmental phrasing anywhere.** No characterizations of the user ("you've been thinking a lot about…"), no AI-narrator voice, no "we noticed". The mirror reflects; it does not commentate. This is the founder's single biggest worry — categorization feeling judgmental is the failure that pulls the revamp.
- **Don't show the themes section in the empty state.** Until enough writing exists for a theme to emerge, the themes section is not rendered at all. The brand block sits directly above the Account block, with the existing styling. No placeholder, no call-to-action, no "your themes appear here" text.
- **Don't add an archive, a "show more", a "view all themes" link, infinite scroll, or pagination.** The sidebar stays short. Three to seven themes max. Old writing lives somewhere else (out of scope for this revamp).
- **Don't ship a long flat list with a header that calls it "Themes".** A header label that fixes the section as "Themes" is fine for accessibility (sr-only), but the visible treatment is just the list of theme labels themselves under the brand block — no visible category heading. The founder's reflection is the content, not a chrome label on top of it.
- **Don't run clustering across users.** Each user's themes are derived only from their own seeds. There is no cross-user signal, no "people who write about X also…", no shared theme taxonomy.
- **Don't ship native mobile in this revamp.** Capacitor / iOS / Android targets are deferred. Web/PWA first; Electron second. If a code path is mobile-only, leave it as-is or behind a feature flag — do not extend it.

## What you're building, in one paragraph

A founder who has been writing in tinker for a while opens the app. The sidebar shows them three to seven short labels — each one a verbatim phrase from their own seed drafts. The labels are the themes that tinker's clustering step has surfaced from their writing. Tapping a label reveals the cluster of writing underneath it. The mirror gets sharper the more they write; that's why they come back. Visually, the sidebar lives inside the same `.sidebar` shell that's there today — same warm-cream surface, same brand block on top, same Account block on the bottom — and reads as calm and home, not a tool with controls.

## Phase plan

The founder has chosen: **Web/PWA ships first, Electron picks it up after, native mobile is dropped from this revamp.**

- **Phase 1 — Web/PWA.** Build everything against `src/renderer/` and the Vercel functions in `api/`. Test in a desktop browser with `npx vercel dev` (the local emulator that runs the auth + functions). At the end of Phase 1, the revamp ships to the hosted website and works for any signed-in user.
- **Phase 2 — Electron desktop (only after explicit founder approval of Phase 1).** Wire the same renderer into the Electron build. The clustering step is server-side via the same `/api/themes` (or whatever it ends up named) endpoint, so the Electron path mostly inherits Phase 1's work — but verify the IPC / preload surface still exposes whatever the new sidebar needs, and that the Electron-only paths in `seeds.js` still feed the clustering input correctly.
- **Native mobile (Capacitor) is not part of this revamp.** Leave the Capacitor code paths alone; do not extend them. If a Capacitor-only code path would break, fix it minimally to keep the existing mobile build working, then move on.

3. **The real clustering step.** Add a new Vercel function — propose `api/themes/index.js` (or pattern-match an existing function name) — that:

Cache the result in `localStorage` so the sidebar renders instantly on next load; refresh in the background on writing close. The mocked data from step 2 is replaced with the real response.

   The clustering response shape must enforce the verbatim rule at the API layer — not just at the prompt layer. The prompt asks for offsets; the function validates them; invalid responses get a single retry and then drop the bad label rather than ship it. Better to show four themes than five themes with one AI-authored label.

## Constraints (non-negotiable)

- **Inside the existing shell.** The `<aside class="sidebar">` in `src/renderer/index.html` stays. The new themes section is a `<nav>` inside it, between `.sidebar__top` and `.sidebar__account`. Visual canon: `src/renderer/styles.css`, `src/renderer/design-tokens.css`, `src/renderer/tokens/rainbow-web.json`. No new fonts, no new color tokens, no new button visuals, no new icon library, no CSS framework, no new sidebar component, no new welcome surface, no new modal stack.
- **Theme labels come from the user's writing, not from the AI.** Every theme label rendered in the sidebar must be a verbatim substring of one of the user's own seeds / drafts / essays. The clustering function returns offsets, not strings; the renderer reads the substring at that offset. Validation runs at the API layer — invalid offsets get dropped, never shipped.
- **Visible-string allowlist.** Every visible string on the rendered sidebar must be one of:
  - (a) a verbatim substring of one of the founder's own seeds / drafts / essays (theme labels and cluster contents), OR
  - (b) one of these fixed UI strings (the only chrome strings the agent may use or keep):
    - `"tinker"` — brand name in `.sidebar__name` (already there)
    - `"Account"` — `.sidebar__account-head` (already there)
    - `"Receipts"` — `.sidebar__account-label` for the receipts button (already there)
    - `"Share tinker"` — `.sidebar__account-label` for the share button (already there, hidden conditionally)
    - `"© 2026 tinker"` — `.sidebar__footer-copy` (already there)
    - `"Themes"` — sr-only accessible label on the new themes `<nav>` (sole new chrome string in this revamp)
  - Anything outside (a) or (b) is a bug. Before considering Phase 1 done, walk every text node in the rendered sidebar and verify each is either a verbatim substring of the user's writing or one of the six strings above. The check is a build step, not a vibe.
- **Empty state is empty.** Below the theme-emergence threshold, the themes `<nav>` is not rendered (or is `hidden`). No placeholder, no CTA, no "your themes appear here" text. The brand block sits directly above the Account block.
- **Stays short.** Three to seven themes maximum. No scroll within the themes section. No "show more". No archive.
- **Per-user only.** Clustering is derived from one user's own writing. No cross-user signal, no shared taxonomy, no public-facing themes.
- **Web/PWA first, Electron second, native mobile out of scope.** Phase 1 ships before Phase 2 starts. Capacitor paths are not extended.
- **The Anthropic key never reaches the browser.** The clustering function holds it server-side, exactly the way `/api/search` does today. Mirror that pattern; do not invent a second key-handling pattern.

## Open questions — ask the founder, don't invent

If any of these is unanswered when you reach the relevant step, stop and ask via the founder rather than picking a default.

1. **Threshold for theme emergence.** How much writing is needed before the themes section appears? A count of seeds? A character threshold? A number of writing sessions? Whatever the answer, it should be a single number the agent can read, not a heuristic that drifts.
2. **Tap destination — sidebar inline or stage takeover?** When the founder taps a theme, does the cluster expand inline in the sidebar (themes stay visible above), or does the stage area to the right swap to a cluster view (the way tapping a seed swaps in the writing flow today)?
3. **Refresh trigger.** Does clustering run on every writing-session close? Once a day? On a manual button? The founder said *"after any writing"* in the interview — interpret strictly (every close) or loosely (debounced / once-per-session-day)?
4. **Cluster contents — what's a "writing"?** A cluster groups items together. Are those items seeds, drafts, essays, or a mix? The clustering input data is the same in any case, but the cluster's surface output (what the user sees when they tap a theme) needs to be one of them or all of them.
5. **Persistence vs recompute.** Are themes persisted (stored via `sync.js` to `/api/user-data/*` so they're identical across devices) or recomputed on each load (fast on cache, slower on cold)? Persistence is more work but means the founder sees the same themes on phone and desktop (Phase 2 onwards) without a recompute lag.
6. **Active-state styling for the tapped theme.** When a theme is the currently-open cluster, what's its visual state? `.sidebar__account-item` has no obvious "active" class today — check `renderer.js` for how the brand button or current section signals selection, and inherit that.
7. **Loading state.** While clustering is running (after writing close), does the sidebar show a quiet loading indicator? The founder ruled out attention-grabbing UI; a faint shimmer on the themes rows is probably right, but confirm before shipping.

If you must move forward without an answer, mark `[NEEDS INPUT]` in a code comment and pick a sensible default — but report it back at the next checkpoint so the founder can correct.
