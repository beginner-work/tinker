# Build the tinker client↔server data-sync layer

> Version: v0.100
> Generated by the founder-package skill (product spec flow).
> Reconstructed from shipped code by the build-prompts audit (2026-05).

Build the layer that round-trips the founder's client-owned localStorage blobs
to the server: `src/renderer/sync.js` (boot-time hydrate + debounced per-kind
push) and the `api/user-data/*.js` endpoints, sharing one GET/PUT handler factory
(`api/_lib/user-data.js`) over a single Prisma table (`api/_lib/db.js`). The
localStorage keys stay the source of truth for the renderer; the server is the
source of truth across devices. Every row lives in the `TinkerUserData` table,
keyed by `(userId, kind)`, and that table is shared with the beginner repo (same
Postgres via `DATABASE_URL` — README → "Shared database with the beginner repo").

## Anti-patterns — do not repeat

- **Don't make the server the live store the renderer reads from.** The
  consumer modules (`seeds.js`, `heatmap.js`, `sidebar-tree.js`, `renderer.js`,
  `pitches.js`) do synchronous localStorage reads. Sync overwrites localStorage
  on hydrate and pushes localStorage on save; it never becomes a read dependency
  in the render path. This keeps offline behaviour and synchronous reads
  unchanged.
- **Don't push on every keystroke.** Pushes are debounced per-kind
  (`PUSH_DEBOUNCE_MS = 1500`) so a typing burst coalesces into one PUT. Each
  flush re-reads the current localStorage at flush time ("last value wins"),
  rather than capturing a stale snapshot when the timer was set.
- **Don't blindly overwrite local state on hydrate.** Two blobs need merge, not
  replace: **drafts** merge by `id` (a draft created by tapping a welcome tile
  before the first hydrate resolves must survive the server's pre-tap response —
  otherwise `renderer.js`'s `tinker:hydrated` listener bounces the writing view
  back to the feed, a visible flicker), and **pitches** fold the local
  `personalTitle` back in per-id when the server copy hasn't seen a not-yet-pushed
  rename. Everything else is whole-blob replace.
- **Don't trust the client's identity claim.** Every endpoint re-validates the
  Bearer token through Stytch's `authenticateSession` and pulls `user_id` out of
  the session response. The `userId` half of the row key is never taken from the
  request body.
- **Don't split a blob into per-record rows or add partial-update semantics.**
  Each kind is one JSON blob in one row; PUT replaces it wholesale. The client
  owns the inner shape; the server just stores JSON. (The 256 KB cap exists to
  catch bugs, not to shard.)
- **Don't migrate `tinker.tree.v1` here.** The tree key is legacy; the live deck
  store is `tinker.pitches.v1`, produced authoritatively by the backend organize
  job. Sync still round-trips both keys, but the tree→pitches migration is owned
  by `pitches.js`, not this layer.

## Read first

- `src/renderer/sync.js` — the whole client layer. The kind/key tables, the
  `apply*FromServer` functions (note `applyDraftsFromServer`'s `mergeById` and
  `applyPitchesFromServer`'s per-id `personalTitle` fold), `fetchKind` /
  `pushKind`, the debounced `schedulePush`, the public `window.tinkerSync` API
  (`pushEssays`, `pushDrafts`, `pushSeeds`, `pushTaxonomy`, `pushTree`,
  `pushPitches`, `flush`, `hydrate`), and the boot/`tinker:auth-changed`/
  `pagehide` wiring. Storage keys: `tinker.essays.v1`, `tinker.drafts.v1`,
  `tinker.seeds.v1` + `tinker.seeds.hidden.v1` (one `{ explicit, hidden }` blob
  server-side), `tinker.taxonomy.v1`, `tinker.tree.v1` (legacy), `tinker.pitches.v1`.
- `api/_lib/user-data.js` — the shared GET/PUT handler factory `makeHandler(kind)`:
  `extractBearer`, `readJsonBody` (256 KB cap → 413), `resolveUserId` (via
  `authenticateSession`), the `prisma.tinkerUserData.findUnique` /
  `upsert` round-trip on the `userId_kind` compound key, and the `{ data,
  updatedAt }` GET / `{ ok, updatedAt }` PUT shapes. GET returns `data: null`
  when no row exists — clients treat null as "nothing stored yet."
- `api/_lib/db.js` — the Prisma singleton (cached on `globalThis` so warm Vercel
  invocations don't exhaust Postgres connections).
- `api/user-data/drafts.js`, `essays.js`, `seeds.js`, `taxonomy.js`, `tree.js`,
  `pitches.js` — each a two-line module: `module.exports = makeHandler("<kind>")`.
  Read the header comments for each kind's blob shape (e.g. `tree` is
  `{ [deckHeading]: [{ writingId, offset, length, addedAt }, …] }`; `pitches` is
  `{ pitches: [...], activeId, _migratedFromTree }`).
- `prisma/schema.prisma` — the `TinkerUserData` model: `userId String`,
  `kind String`, `data Json @default("null")`, `updatedAt`, `@@id([userId, kind])`,
  `@@index([userId])`. The header notes the canonical schema lives in the
  beginner repo; this file mirrors only the one table the web functions touch.
- `api/_lib/stytch.js` — `authenticateSession`, the validation seam every
  endpoint shares (full detail in `auth-phone-pin.md`).
- `src/renderer/renderer.js` — the `saveDrafts`/`saveEssays` call sites that fire
  `window.tinkerSync.pushDrafts()` / `pushEssays()`, and the `tinker:hydrated`
  listener that re-reads after a hydrate. `src/renderer/pitches.js` and
  `sidebar-tree.js` are the other push callers.
- `README.md` (the "Shared database with the beginner repo" section),
  `package.json` (the `postinstall: prisma generate` + `db:migrate` scripts),
  `vercel.json` (`buildCommand: prisma migrate deploy`).

## What you're building, in one paragraph

`sync.js` boots when a `tinker_jwt` token is present (after `auth.js` shows its
gate on the web, the `tinker:auth-changed` event catches first-time sign-in too;
on Electron/Capacitor there's no token and `hydrate()` returns early). `hydrate()`
GETs all six kinds in parallel, applies each to its localStorage key (drafts
merge by id, pitches fold local `personalTitle`, the rest replace), and dispatches
`tinker:hydrated` so the consumer modules re-render from refreshed storage. After
any local change, a consumer calls the matching `window.tinkerSync.push*()`,
which schedules a 1500ms-debounced PUT that re-reads the current localStorage at
flush time; `pagehide`/`visibilitychange`/`tinker:auth-changed` force an immediate
`flush()` of all pending pushes so the tail of a typing burst isn't dropped.
Server-side, each `api/user-data/<kind>.js` is one line over `makeHandler(kind)`,
which validates the Stytch Bearer token, resolves the `user_id`, and reads or
upserts the single `TinkerUserData` row at `(userId, kind)` — the client owns the
JSON shape; the server only stores it. That table is shared with the beginner
repo, so the same row store backs both apps.

## Build sequence

1. **The Prisma singleton + schema.** Write `prisma/schema.prisma` mirroring the
   `TinkerUserData` model (`@@id([userId, kind])`, `@@index([userId])`,
   `data Json @default("null")`, `binaryTargets = ["native",
   "rhel-openssl-3.0.x"]` for the Vercel runtime) and `api/_lib/db.js` (cache the
   `PrismaClient` on `globalThis.__tinkerWebPrisma`). Wire `postinstall: prisma
   generate` and `db:migrate: prisma migrate deploy` in `package.json`, and
   `buildCommand: prisma migrate deploy` in `vercel.json`. Point `DATABASE_URL`
   at the shared Postgres (README → "Shared database with the beginner repo").
   **CHECKPOINT — stop and report.** Confirm `prisma generate` runs in
   `postinstall`, the table key is the `(userId, kind)` compound, and the schema
   header notes the canonical copy lives in beginner. Get confirmation that
   `DATABASE_URL` targets the shared endpoint before any write.

2. **The handler factory — `api/_lib/user-data.js`.** Build `makeHandler(kind)`:
   reject non-GET/PUT (405 + Allow); `resolveUserId(req)` via `extractBearer` +
   `authenticateSession`, pulling `user_id` from `session.session.user_id` or
   `session.user.user_id` (401 if missing); on GET return `{ data: row?.data ??
   null, updatedAt }`; on PUT parse the body with `readJsonBody` (256 KB →
   413; invalid JSON → 400), require a `data` field (400 otherwise), and
   `prisma.tinkerUserData.upsert` on `{ userId_kind: { userId, kind } }`
   returning `{ ok: true, updatedAt }`. Wrap in `withResponseLogging`. This one
   factory is the entire server-side surface — the endpoints are trivial.

3. **The six endpoints.** Write `api/user-data/drafts.js`, `essays.js`,
   `seeds.js`, `taxonomy.js`, `tree.js`, `pitches.js` — each
   `module.exports = makeHandler("<kind>")` with a header comment documenting its
   blob shape and whole-blob semantics. Note the `seeds` kind stores one
   `{ explicit, hidden }` object server-side even though the client keeps two
   localStorage keys; the `pitches` blob's AI-shaped fields (`aiTitle`, rehomed
   deck contents) are owned by `api/pitches/organize.js`, with PUT carrying only
   user-controlled fields (`personalTitle`, `activeId`, `expanded`) between
   organize runs.
   **CHECKPOINT — stop and report.** With a valid `tinker_jwt`, confirm GET on a
   fresh user returns `{ data: null }`, PUT then GET round-trips a blob, a missing
   `data` field 400s, an oversized body 413s, and a bad token 401s. Verify the
   same row is visible from the beginner side (shared table) before relying on
   cross-repo flows — README notes beginner previews read a branched DB, so
   verify on production.

4. **The client layer — `sync.js`.** Build the kind/key tables and the
   `apply*FromServer` functions: whole-blob replace for essays/seeds/taxonomy/
   tree, `mergeById(local, server)` for drafts (preserve local-only drafts;
   server wins for ids it already knows; sort by `createdAt` desc), and the
   per-id `personalTitle` fold for pitches. Build `fetchKind`/`pushKind` (Bearer
   `tinker_jwt`; GET reads `json.data`; PUT sends `{ data }`), the debounced
   `schedulePush` (re-read localStorage at flush time), and the public
   `window.tinkerSync` API: `pushEssays`, `pushDrafts`, `pushSeeds`,
   `pushTaxonomy`, `pushTree`, `pushPitches`, `flush` (clear timers + fire all
   pending immediately), and `hydrate` (parallel GET of all six → apply →
   dispatch `tinker:hydrated` if anything changed).

5. **Boot + lifecycle wiring.** Kick `hydrate()` on DOMContentLoaded if a token
   exists (so consumer modules have registered their `tinker:hydrated` listeners
   first), re-`hydrate()` on `tinker:auth-changed` (catches first-time sign-in),
   and `flush()` on `pagehide` and on `visibilitychange → hidden` (capture the
   last keystroke before a tab close). Confirm `renderer.js`'s `saveDrafts` /
   `saveEssays` call `pushDrafts()` / `pushEssays()`, and that `pitches.js` /
   `sidebar-tree.js` call `pushPitches()` / `pushTree()` after their commits.
   **CHECKPOINT — stop and report.** Sign in on one device, write a draft, sign in
   on a second; confirm the draft hydrates over. Tap a welcome tile to create a
   draft during the boot window and confirm it isn't dropped by the first
   hydrate (no writing-view flicker back to the feed). Rename a pitch and confirm
   the `personalTitle` survives a racing hydrate.

## Constraints (non-negotiable)

- **localStorage is the renderer's source of truth; the server is the
  cross-device truth.** Sync only overwrites-on-hydrate and pushes-on-save. It is
  never a synchronous read dependency in the render path.
- **One JSON blob per `(userId, kind)` row; PUT replaces wholesale.** No per-
  record rows, no partial updates. The client owns the inner shape. 256 KB cap →
  413.
- **Server resolves `userId` from the validated Stytch session, never from the
  body.** Every request re-validates the Bearer `tinker_jwt` via
  `authenticateSession`; a missing/invalid token is 401.
- **Pushes are debounced 1500ms per-kind and re-read state at flush time.** A
  burst coalesces to one PUT (last value wins). `flush()` fires all pending
  immediately on auth-change / pagehide.
- **Drafts merge by id; pitches fold local `personalTitle`; all other kinds
  replace.** These two merges are load-bearing against the boot race and the
  rename race respectively — do not collapse them to plain overwrite.
- **The six kinds are fixed:** `essays`, `drafts`, `seeds`, `taxonomy`, `tree`,
  `pitches`. `seeds` is one `{ explicit, hidden }` blob server-side; `tree` is
  legacy (migration owned by `pitches.js`).
- **`TinkerUserData` is shared with the beginner repo.** Same Postgres via
  `DATABASE_URL`. Don't rename the table or change its key; schema changes must
  stay compatible with both repos (canonical schema is beginner's).
- **No new model calls in this layer.** This is plain CRUD over a JSON column —
  no Claude calls live here. (For reference, model ids elsewhere in this repo are
  `claude-opus-4-7` in `api/claude/converse.js` and `claude-haiku-4-5-20251001`
  in the classify/search/feed functions; never `claude-sonnet-4-6`.)

## Done when

- `hydrate()` GETs all six kinds in parallel for a signed-in user, applies each
  to its localStorage key, and dispatches `tinker:hydrated`; consumer modules
  re-render from refreshed storage.
- A draft created during the boot window survives the first hydrate (merged by
  id, no writing-view flicker); a not-yet-pushed pitch `personalTitle` survives a
  racing hydrate.
- After a local change, the matching `window.tinkerSync.push*()` PUTs a debounced
  blob; `flush()` on `pagehide` / auth-change drains pending pushes.
- Each `api/user-data/<kind>.js` round-trips its blob: GET returns
  `{ data, updatedAt }` (null on a fresh user), PUT `{ data }` returns
  `{ ok, updatedAt }`; non-GET/PUT 405s, missing `data` 400s, oversized body
  413s, bad token 401s.
- `userId` is always resolved from the validated Stytch session, never the body;
  every row lands at `(userId, kind)` in `TinkerUserData`.
- The same row is readable from the beginner repo (shared table), verified on
  production.
- On Electron/Capacitor (no token) `hydrate()` returns early and nothing syncs.
