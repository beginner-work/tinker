**This revision (v0.102) replaces v0.101's design.** One thing changed:

1. **The Receipts section is renamed to Money market funds, with money-market-style framing on the same underlying data.** No new backend, no real MMF integration. `transactions.js` keeps its data shape and its render entry point. What changes is the section title (in the dashboard and anywhere else it appears), the framing language used to describe the section, and the vocabulary used for the rows inside it (subscription payments become *deposits*; the running total becomes *balance*; the framing pulls on the founder's own line: *"money → a way to see their investments in writing grow"*). The MMF metaphor reframes payments as deposits into the user's writing-investment fund; there is no actual yield, no actual fund vehicle. This is reframing, not a new product.

**Carried over from v0.101 (replaced v0.100's design).** Four things changed from v0.100:

1. **Single sidebar entry, single page.** v0.100 kept multiple entry-point rows (`Receipts`, `LinkedIn fits`, plus a new `Plan` row) in the sidebar's account section, each opening its own workshop view in the stage. v0.101 collapses that: one entry row in the sidebar opens one newly designed Account page that contains all the sections.
2. **The onboarding is a setup form, not a slideshow.** v0.100's first-tap experience was a 3–5 slide tour. v0.101 replaces it with a small functional setup form that asks the user for their **name** and their **LinkedIn account**, then saves. No tour.
3. **The page header carries the at-a-glance state.** After setup, the top of the Account page shows the user's **name** and **plan tier**. Money market funds, LinkedIn fits, plan-tier picker, and future widgets sit as sections below the header on the same page.
4. **The sidebar row labels itself by state.** Until setup is complete, the row reads *"Account setup"* (the founder's exact words: *"the initial showing should say account setup"*). After setup, it reads *"Account"* with the user's name underneath (or in a secondary line — pick the cleanest layout that fits `.sidebar__account-item`'s sizing).

The hidden `nav-share` row stays where it is, gated by `share.js`'s existing PWA/Capacitor check. Share is a different beast (a one-tap action, not a section to view), and folding it into the page would muddy the gating. Stays as a separate row.

## Anti-patterns — do not repeat

- **Don't keep `nav-receipts` and `nav-linkedin` as separate sidebar rows.** v0.100's design did. v0.101 explicitly collapses them onto the Account page. The two buttons are removed from the sidebar in step 1.
- **Don't call the money-market-funds section "Receipts" anywhere visible.** v0.102's rename is total — section title, sidebar mentions, dashboard, setup-form intro copy if it mentions the section. The underlying module name (`transactions.js`) doesn't need renaming — that's a file path, not a visible string — but every text node the user sees uses *Money market funds*, *deposit*, *balance*, and the founder's reframing line.
- **Don't invent yield, returns, or interest figures.** The Money market funds metaphor reframes payments as deposits into the user's writing-investment fund; it does not promise financial returns. No yield percentage, no "your fund earned $X this month", no APY. Misleading users about returns is a serious bug. If a number isn't a verbatim deposit amount, a sum of deposit amounts, or a count of deposits, it doesn't render.
- **Don't ship a tour-style onboarding.** v0.100 had a 3–5 slide tour. v0.101 has a setup form. If a slide deck is in the build path, that's the v0.100 design leaking back in — strip it.
- **Don't ask for more than name + LinkedIn account in setup.** The founder named those two fields. Don't add email (Stytch already has it), don't add company name, don't add bio, don't add avatar upload. Two fields. If a future widget needs a value the user hasn't given, that widget asks for it inline, not in setup.
- **Don't make setup skippable on the first session.** Tapping the Account row pre-setup goes straight to the setup form; there's no "skip for now" button. The label *"Account setup"* on the sidebar row is the truthful description — until setup is done, the page is the form. (Open question 5 below: should there be a back/escape to the rest of the app? Default yes, via the stage's existing close-section affordance.)
- **Don't ship useless sections.** Founder's line: *"no useless sections — everything has high utility that you'd want to keep up to date with."* Every section on the dashboard earns its place. If a section is here "because dashboards have one", cut it.
- **Don't make the controls clunky.** Founder's risk: *"clunky controls that are not fun."* Toggles toggle in one tap. Copy buttons copy on tap with a small in-place confirmation, not a modal. The setup form's *Save* button saves and re-renders, not a multi-step confirm.
- **Don't render the dashboard as a settings form.** Sections are sections, not stacked labeled `<form>` rows. They carry their own visual weight via the focused-workshop chrome.
- **Don't ship AI-generated marketing or upsell copy.** Plan section shows tier names and prices verbatim from `pitch-deck.md` slide 10 (*"$7, $35, $70 — and enterprise-level pricing beyond that"*). No "Unlock your potential!" microcopy on the Plan section, the page header, or the setup form.
- **Don't ship a flow between sections.** The page is a workspace, not a checklist. No "next section" button at the bottom of Receipts pointing to LinkedIn fits. The user picks what to touch.
- **Don't introduce new fonts, colors, button visuals, or a CSS framework.** Visual canon is `src/renderer/styles.css`, `src/renderer/design-tokens.css`, `src/renderer/tokens/rainbow-web.json`. New widget classes extend the existing tokens.
- **Don't ship native mobile or Electron in this build.** Web/PWA only. If a code path is Electron-only or Capacitor-only, leave it alone.
- **Don't author labels for widget values.** Receipt amounts, fit counts, plan names — they come from their source. Don't wrap a number in editorialized phrasing.
- **Don't fold the Share row into the Account page.** Share stays a separate sidebar row, gated by `share.js`. The Account page is for sections the founder keeps up to date with; Share is a one-tap action.

## What you're building, in one paragraph

A founder opens tinker. The bottom of the sidebar has one Account row (and the hidden Share row, in PWA/Capacitor). On a fresh account the row reads *"Account setup"*. Tap it: the stage shows a small setup form — two fields, *Name* and *LinkedIn account*, and a save button. Save: the row's label becomes *"Account"* with the user's name shown on the row, and the page re-renders into the dashboard state. The dashboard's top shows the user's name and their plan tier, drawn directly from the founder's deck (*Free to start*, *$7*, *$35*, *$70*). Below the header, sections sit on the same page in a focused-workshop layout: **Money market funds** (the existing `transactions.js` content rendered inside the new workshop chrome, with each payment reframed as a *deposit* into the user's writing-investment fund), LinkedIn fits (the existing `linkedin-fit.js` content rendered the same way), Plan (a new tier-picker), and future sections. Each section is visibly its own thing — separators between them, affordances on every control, accent colors drawn sparingly from the rainbow-web token set in the way an IDE colors syntax. The whole page reads as a workshop tucked inside tinker's quiet home, with the user's identity at the top and the high-utility sections below.

## Mood — how it should feel

Founder's word: **focused workshop**. The rest of tinker is a quiet home (warm cream, low contrast, soft hovers). The Account page is the workshop tucked inside that home — denser, more deliberate, more colorful.

What carries this mood (per the founder's UI cues):

- **Clear row separators between controls.** Each section on the dashboard is visibly its own thing — a thin border or a defined gap between sections, not a continuous flow. Inside each section, individual widgets are also separated.
- **Visible affordances on every control.** A toggle looks like a toggle at rest; a copy button has a clipboard glyph; a tier card has a clearly-tappable tier-pick affordance. No control is so minimal that the user has to hover to discover what it does. The setup form's two fields have clear labels and a clearly-tappable Save button.
- **Working spaces that are colorful like an IDE.** Pull from the rainbow-web token set already in `tokens/rainbow-web.json`: the muted cream stays as base, but section accents (the section's left-border or category marker) and widget accents (status chips, active states) use the brand's pink / orange / yellow / green / blue / purple sparingly, in the way an IDE colors syntax. The colorfulness is a function of the controls present, not added decoration.

What this mood is NOT:

- Not a quiet-home panel. The rest of tinker is calm; the Account page is purposeful. Tighter spacing, more visible state.
- Not a corporate dashboard. No KPI cards, no big numeric tiles with growth percentages, no "executive summary" panel above the page header.
- Not a settings page. No `<form>` of stacked labeled rows on the dashboard. (The setup form *is* a tiny form by necessity, and that's fine — but the dashboard is sections, not a form.)
- Not gamified. No streaks, no badges, no XP, no "achievement unlocked" toasts.

## Build sequence

## Constraints (non-negotiable)
