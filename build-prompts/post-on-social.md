# Build Post on Social

> Version: v0.100
> Generated by the founder-package skill (product spec flow).

Build the v1 of **Post on Social** from this prompt. The founder has worked through a guided interview that distilled the idea into the structure below; this is the imperative form a build agent executes against.

Post on Social **replaces** the existing stitching feature at `src/renderer/linkedin-fit.js`. Delete that file and rebuild as the new feature. The old feature stitched verbatim essay fragments + AI bridges into a 1080×1080 PNG meant to be posted on LinkedIn. That model is gone. The new feature **never generates post text in any form** — its job is to get the founder oriented, then hand them to a real composer where they write the post in their own words.

The feature is **agnostic to the social platform**. Each session, the founder picks where they're posting (LinkedIn, X, Bluesky, Threads, Substack Notes, Other); the verdict and prompt are scored for that platform.

Single-phase build, web/PWA only. The same `src/renderer/` is served by Electron desktop and Capacitor mobile shells; no platform-specific work.

## Anti-patterns — do not repeat

- **Don't generate post text. Not a draft, not a "suggested post," not a "polish my post" affordance, not a stitched verbatim+AI post, not a paginated image of one.** The old `linkedin-fit.js` did this; that's the line the founder is now drawing. The model produces a verdict (score + reason) and one reader-POV question. Nothing the model writes ever appears in the composer or is positioned as something to post. The founder writes every word that lands in the composer.
- **Don't render essay text as an image.** Delete the entire canvas pipeline (`IMG_W`, `IMG_H`, `IMG_MARGIN`, `IMG_HEADER_H`, `TINKER_MARK_SVG`, `IMG_VERBATIM_FONT`, all the `draw*` helpers). The old feature treated the essay as a poster. The new feature treats the essay as the founder's own writing they keep in tinker.
- **Don't lock to LinkedIn.** No copy on the verdict screen names a single platform. No icon assumes LinkedIn. The chooser is the only place a platform name appears in the chrome; the verdict screen says "this would land here" with the chosen platform substituted by name. If you find yourself writing `LinkedIn` as a literal anywhere outside the platform chooser, the chosen-platform string, or the API prompt, stop — that's a regression of the old feature.
- **Don't make it a library or a daily habit.** The founder explicitly said *"When the impulse hits"* — this is not a place they live in daily. Each session is a clean, short pass. No "what's new since last visit," no "your top picks today," no auto-score on mount of every essay against every platform. Score lazily, for the chosen platform only, when the verdict screen renders.
- **Don't add notifications, daily prompts, "top pick of the day," or progress meters.** Founder verbatim: *"No notifications, daily prompts, or 'what's next' beckoning."* The page is composed by the founder's impulse, not driven by an external pull.
- **Don't add engagement prediction or virality scoring.** No "predicted likes," no "will go viral," no follower-count signals. Founder verbatim: *"No engagement prediction or virality scoring."* The verdict is about whether the writing belongs out there — not about chasing reach.
- **Don't pre-fill the composer with text.** Per F4: *"Just the strongest essay and a 'you're ready' nudge."* The composer button opens the platform's compose URL **with no `text=` parameter**, in a new tab. The founder writes the post from scratch. The tinker tab stays open with the essay and the reader-POV question visible as reference.
- **Don't make the prompt generic.** Founder named this as the failure mode: *"At the one prompt — it doesn't help me."* The reader-POV question on step 3 must be drawn from the specific essay's content — a concrete observation about something IN that essay that a scroller would notice. If the model returns something generic ("what would your reader think?"), the prompt asks again or shows the verbatim reason instead — never ships a generic question.
- **Don't introduce new fonts, colors, button visuals, icon libraries, or a CSS framework.** Visual canon is `src/renderer/styles.css` + `src/renderer/design-tokens.css` + `src/renderer/tokens/rainbow-web.json`. Rename the `.linkedin-fit__*` namespace to `.post-on-social__*` and keep the visual language; do not author parallel design tokens.
- **Don't add multiple primary actions per screen.** Concrete mood cue: *"One clear primary action per screen."* Step 1 has one action (pick a platform → advance). Step 2 has one action (continue → step 3). Step 3 has one action (open the composer). Nothing competes.

## What you're building, in one paragraph

Post on Social is a three-step flow the founder opens when they feel the impulse to share something on social. Step 1: a platform chooser — LinkedIn, X, Bluesky, Threads, Substack Notes, Other — labeled *"Where are you posting?"*. Step 2: a verdict screen showing the founder's published essays scored 1–10 for the chosen platform, sorted strongest-first, with a short reason per essay drawn from the essay itself. Step 3: a prompt screen surfacing the strongest essay and a single reader-POV question — a concrete observation a scroller would notice in *that specific essay* — with one button that opens the chosen platform's composer in a new tab. The composer arrives empty; the founder writes the post in their own words, with the prompt-screen tab still open as reference. The model never writes post text; the model produces a score, a reason, and a question, and nothing else.

## Phase plan

**Single-phase build.** Target web/PWA only. The same `src/renderer/` is served by Electron desktop and Capacitor mobile shells; no platform-specific work, no native code path.

## Build sequence

1. **Delete and rename the existing surface.** Delete `src/renderer/linkedin-fit.js`. Rename the mount section, the sidebar nav button, and the script tag in `src/renderer/index.html` (paths and ids per the *Read first* section). Rename the variable, the function, and the global in `src/renderer/renderer.js`. Rename the sync hooks and key in `src/renderer/sync.js`. Rename the API file at `api/user-data/linkedin-pitch-draft.js` to `api/user-data/post-on-social.js` and update the storage key inside. Verify the app loads, the sidebar shows "Post on Social," clicking it shows an empty section. Nothing else should be broken.

   **CHECKPOINT — stop and report.** Run the dev server (`npm run dev` for desktop with DevTools, or `npx vercel dev` for the auth-gated web build). Sign in, open Post on Social from the sidebar. Confirm: the page renders empty, no console errors, no other page is broken. Old caches at `tinker.linkedinPitchDraft.v1` can be ignored — they're abandoned (don't write a migration; the old data was a draft, not user content worth keeping).

2. **Build step 1 — the platform chooser.** When `window.tinkerPostOnSocial.render()` is called and there's no chosen platform yet, render the platform chooser inside `<section id="post-on-social">`. Layout:

   - A step indicator at the top: `1 / 3` (small, muted; tightly tracked typography per the mood cue).
   - The screen title: `Where are you posting?`
   - A grid (or vertical list on narrow widths) of platform tiles. The default platform list is:
     - LinkedIn
     - X
     - Bluesky
     - Threads
     - Substack Notes
     - Other
   - Each platform tile is a single button. Clicking advances to step 2 with the chosen platform stored in module-level state. No "Continue" button — picking IS the action. (Concrete mood cue: one clear primary action per screen.)
   - `Other` opens a small inline text input where the founder types the platform name. The verdict step still runs for an unknown platform — the score is generic-prose-with-a-platform-named.

   Persist the chosen platform per session in module state only (not in localStorage). Reopening the page resets to step 1. This is intentional — *"When the impulse hits"* means each session is a fresh decision about where the impulse is pointing.

3. **Build step 2 — the verdict screen.** When a platform is chosen, render the verdict. Layout:

   - Step indicator: `2 / 3`.
   - A title that names the platform: `Reading your essays for {platform}…` while loading, then `For {platform}, this is what would land:` once verdicts arrive.
   - A list of essays, sorted strongest-first by score. Each row:
     - The essay title (or first 8 words of body if no title — reuse the existing `fitTitleFor` pattern from the old file before deleting it; keep that helper locally).
     - A score chip: `{N}/10`.
     - A short reason in the founder's voice — drawn from the essay (the model is told to ground the reason in a phrase from the essay; this prevents generic reasons).
     - A `Read →` affordance that opens the essay in the existing read view (calls into the existing `showRead(essay)` path via the global, or via a new helper on `window.tinkerPostOnSocial`).
   - A primary button at the bottom: `Continue with the top pick →`. Clicking advances to step 3 with the strongest-scored essay.
   - Caching: write each verdict to `tinker.postOnSocial.v1` keyed by `{essayId}::{platform}`. Reopening the same platform on a return visit shows cached verdicts immediately; new essays since last visit show loading dots, then resolve.

   The score loop reuses the concurrency-3 pattern from the old `checkAll` (read it before deleting). The Claude call goes to a new endpoint `api/post-on-social/index.js` that takes `{ platform, essay }` (single essay per call, for streaming UX) and returns `{ fit, score, reason, reader_question, scorer_model }`. Score is an integer 1–10; `fit` is the boolean `score >= 7` (or whatever threshold lands well after the founder uses it once — start with 7, leave `[NEEDS INPUT: confirm the fit threshold after founder tests it]`).

   **CHECKPOINT — stop and report.** Score at least three essays for at least two platforms. Confirm: the verdict reasons read as specific (each names something IN the essay) and not generic; the scores feel directionally right to the founder; the cache holds across reloads.

4. **Build step 3 — the prompt screen.** This is the centerpiece — the founder named this as the make-or-break screen (*"If you could build only one screen, which?"* → *"The prompt screen (step 3)"*). Layout:

   - Step indicator: `3 / 3`.
   - The chosen essay's title.
   - The reader-POV question, large and centered: the `reader_question` field from the verdict. **This is the prompt that has to land.**
   - A small `Read the essay again` link beneath it that opens the essay in the existing read view (in a way that lets the founder return — open in a side panel or a new tab if simpler).
   - The primary button: `Open the {platform} composer →`. Clicking opens the platform's compose URL in a new tab with `window.open(url, "_blank", "noopener,noreferrer")`. The button does **not** copy anything to the clipboard. The composer arrives empty.

   Compose URLs per platform (the safe, documented intents):

   - **LinkedIn**: `https://www.linkedin.com/feed/?shareActive=true` (no `text=` parameter — we are not pre-filling)
   - **X**: `https://x.com/intent/post` (no `text=`)
   - **Bluesky**: `https://bsky.app/intent/compose` (no `text=`)
   - **Threads**: `https://www.threads.net/intent/post` (no `text=`)
   - **Substack Notes**: `https://substack.com/notes` (no documented intent; opens the Notes home where the composer lives)
   - **Other**: no `window.open` — instead, show a tiny inline note: `Open {platform} in another tab and post from there.` The button is suppressed for `Other` since we don't know the URL.

   The tinker tab stays open; the founder writes the post in the platform's composer with the reader-POV question visible in the prior tab.

   **CHECKPOINT — stop and report.** End-to-end: pick LinkedIn → see verdicts → continue with top pick → see the reader-POV prompt → open LinkedIn composer in a new tab → write a post in your own words with the prompt visible in the tinker tab → post. Confirm with the founder that the prompt actually moved them past the cold-composer feeling.

5. **Wire the Claude prompt for scoring + reader-POV question.** The new server endpoint `api/post-on-social/index.js` calls Claude (model: `claude-haiku-4-5-20251001`, same as the existing `api/classify/index.js`). System prompt (sketch — refine when implementing):

   > You score a single piece of writing for how well it would land as a post on a specific social platform. The writer is not asking you to write the post — they will write it themselves in their own words. You give:
   >
   > 1. `score`: an integer 1–10. 10 means "this would absolutely land on this platform"; 1 means "this would not land — too long, wrong register, wrong topic for that audience." Score conservatively. Most essays should be 4–7.
   > 2. `reason`: one short sentence that explains the score by referencing something specific IN the essay. Quote a phrase from the essay if a phrase carries the reason. Never generic ("strong voice," "good topic"). Always concrete ("the line about your barber handing you a hundred dollars is the kind of receipt that lands here").
   > 3. `reader_question`: one short question that points the writer at a concrete observation a scroller would notice in THIS essay. The question is for the writer to chew on before they open the composer — it gives them an angle. Never generic ("what would your reader think?"). Always specific ("what does it feel like to be your barber in that moment — could you open with that?").
   >
   > Respond with one JSON object: `{"score": N, "reason": "...", "reader_question": "..."}`. Never wrap in code fences. Never add explanation outside the JSON.

   Per-platform tuning: include the platform name in the user message ("The platform is X. The writing is below."). The model adjusts register awareness (LinkedIn = longer, professional; X = punchy, short; Bluesky = casual, conversational; Threads = personal, low-stakes; Substack Notes = short, literary). Do not author per-platform sub-prompts — one prompt, the platform name as input.

6. **Visible-string allowlist.** Before declaring done, open every screen of the rendered page and verify every text node is one of:

   - (a) verbatim from the founder's essay (the row title via the snippet helper),
   - (b) the model's verdict fields parsed from JSON (`reason`, `reader_question`, `score`),
   - (c) the chosen platform name as the founder picked it (substituted into the templates below),
   - (d) a fixed UI string from this allowlist:

     - `Post on Social` (sidebar label, mount section aria-label)
     - `1 / 3`, `2 / 3`, `3 / 3` (step indicators)
     - `Where are you posting?` (step 1 title)
     - `LinkedIn`, `X`, `Bluesky`, `Threads`, `Substack Notes`, `Other` (platform tile labels)
     - `Name the platform` (placeholder on the Other input)
     - `Reading your essays for {platform}…` (step 2 loading title)
     - `For {platform}, this is what would land:` (step 2 loaded title)
     - `{N}/10` (score chip)
     - `Read →` (open-essay affordance on a row)
     - `Continue with the top pick →` (step 2 primary)
     - `Read the essay again` (step 3 secondary link)
     - `Open the {platform} composer →` (step 3 primary)
     - `Open {platform} in another tab and post from there.` (Other platform fallback)
     - `No published essays yet. Finish a draft first.` (empty state)
     - `Couldn't read this one.` (per-essay error)
     - `Try again` (per-essay retry button)

   Anything outside (a), (b), (c), or (d) is a bug. Replace with the closest allowlisted phrase, or, if a new string is genuinely needed, add it to the allowlist with a one-line justification in a code comment. **The model never writes post text** — no string that would plausibly be pasted into a composer comes from the model.

7. **Style each screen.** Reuse `.post-on-social__*` (renamed from `.linkedin-fit__*`). Specifics:

   - **Step indicator** (`1 / 3`): small uppercase tracking, muted color (`--color-muted` or equivalent), top of each screen. No background, no border — just the numbers and the slash. This is the concrete mood cue the founder picked.
   - **Platform tiles** (step 1): a 2- or 3-column grid on desktop, single column on narrow widths. Each tile is a plain button with the platform name, generous tap target, hover state defined (`background` shifts, slight `transform`).
   - **Verdict rows** (step 2): the existing row layout from the old file is the reference (title + score chip + reason on one row, actions on the right). Clear bottom border between rows — *not* card backgrounds. The "Strongest pick" implicitly is the top row; no badge needed (the sort order carries it).
   - **Prompt screen** (step 3): the most generously spaced screen. The reader-POV question is the visual centerpiece — large display type (Fraunces or whatever the design tokens specify), max-width around 640px, centered. The button below has the strongest hover/active state of any button in the feature (this is THE action).
   - **Single primary action per screen**: enforce this. If a screen would have two primary buttons, demote one to a secondary (text link).

8. **Test the loop end to end.** From a logged-in state with at least three published essays: (a) open Post on Social, see the chooser, (b) pick LinkedIn, see the verdict screen score the essays for LinkedIn, (c) continue with the top pick, see the prompt screen with a specific reader-POV question, (d) open the LinkedIn composer in a new tab, (e) keeping the tinker tab open as reference, write a post in your own words, (f) post it, (g) come back to tinker the next day on a different impulse, pick X this time, confirm the verdict is re-scored for X (different sort order is expected; the same essay may rank differently for X than for LinkedIn). If the loop works without ever asking the user to lean on AI-written text, ship it.

## Constraints (non-negotiable)

- **No AI-written post text, anywhere.** The model produces a score, a reason, and a question. The composer always opens empty. The founder writes every word that ends up in the post.
- **Platform-agnostic.** No hardcoded LinkedIn behavior outside the chooser, the platform-name substitution, and the per-platform compose URL.
- **Inside the existing renderer.** Files touched: `src/renderer/post-on-social.js` (new, replaces `linkedin-fit.js`), `src/renderer/styles.css` (rename + new screen styles), `src/renderer/sync.js` (rename hooks, new key), `src/renderer/renderer.js` (rename variable/function/global), `src/renderer/index.html` (rename mount, nav label, script src), `api/user-data/post-on-social.js` (renamed from `linkedin-pitch-draft.js`), `api/post-on-social/index.js` (new server endpoint for scoring).
- **Visual canon is the existing tinker app.** `src/renderer/styles.css` + `src/renderer/design-tokens.css` + `src/renderer/tokens/rainbow-web.json`. No new fonts, no new color tokens, no CSS framework, no new icon library.
- **Step indicator at the top of every screen.** `1 / 3`, `2 / 3`, `3 / 3`. The concrete cue the founder picked for "focused workshop" mood.
- **One clear primary action per screen.** Nothing competes.
- **Cache by essay × platform.** `tinker.postOnSocial.v1` keyed by `{essayId}::{platform}`. Synced via `sync.js`.
- **No daily prompts, no notifications, no "what's next" beckoning, no engagement prediction, no virality scoring, no follower counts.**
- **No image rendering of essay text. No canvas pipeline.** Delete every trace from the old file.
- **No `tinker:writing-saved` listener.** The page does not auto-refresh when essays are written elsewhere. It's opened on impulse; it loads what's there at open time.

## Open questions — ask the founder, don't invent

- **Fit threshold.** Is `score >= 7` the right cutoff for what counts as "would land"? Or 6? Or 8? Founder should use the verdict screen for one real session before this is fixed. For v1, start with 7 and observe.
- **Substack Notes intent URL.** As of this build, Substack doesn't expose a documented compose intent URL. The fallback opens `https://substack.com/notes` (the Notes feed). If Substack ships an intent URL, swap it in. If not, consider whether to remove Substack from the default list or keep it with the fallback.
- **Other-platform handling.** When the founder picks `Other` and names a platform, we don't have a compose URL. Current behavior: suppress the composer button, show a one-line note. Alternative: try a search for the platform's compose URL. For v1, the one-line note is honest — confirm before adding anything more.
- **Icon for the sidebar nav.** The current `#nav-linkedin` icon is a stylized LinkedIn glyph. For a platform-agnostic feature, a paper-plane, share-arrow, or compose-pencil glyph would read better. Founder should pick before v1 ships.
- **Read-the-essay affordance on step 3.** The "Read the essay again" link could open the essay in a new tab (preserves the prompt-screen as reference) or open the existing in-app read view (clean but loses the prompt visibility). Recommend new tab for v1; founder can change after one session.
- **What happens if no essays exist?** Step 2 shows the empty state: `No published essays yet. Finish a draft first.` Should the platform chooser even appear in that case, or should the empty state come first? For v1, show the chooser anyway — the founder may want to confirm the page works before they have content.
- **Should the platform chooser remember the last-used platform across sessions?** Default: no — reset to step 1 each time, per *"When the impulse hits."* But if returning to the same platform repeatedly becomes a chore, a small "Last time: LinkedIn" hint above the chooser could help without driving the choice.

If you must move forward without an answer, mark `[NEEDS INPUT]` in a code comment and pick a sensible default.
