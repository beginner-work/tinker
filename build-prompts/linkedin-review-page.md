# Build the LinkedIn writing review page revamp

> Version: v0.100
> Generated by the founder-package skill (product spec flow).

Build the v1 of the revamped LinkedIn writing review page from this prompt. The founder has worked through a guided interview that distilled the idea into the structure below; this is the imperative form a build agent executes against.

This is a revamp of the existing page at `src/renderer/linkedin-fit.js`, mounted at `<section id="linkedin-fit">` in `src/renderer/index.html`. It is not a greenfield page. The reframe is two changes:

1. The page becomes **a permanent library the founder lives in daily**, not a one-shot scanner. On first arrival with essays present, the library auto-scores so the user lands in a populated workshop — not a "Read each one" cold-start. On return, new essays written since last visit show up scored without a manual click.
2. **A high-scoring essay gets a "Post to LinkedIn" action** that opens LinkedIn's composer with the essay text. This closes the loop the founder cares about — the moment the user goes from "scrolling LinkedIn" to "posting on LinkedIn", with their own essay unaltered. **No AI rewriting of any kind.** The essay is what gets posted.

Single-phase build, web/PWA only. The Electron and Capacitor shells already serve the same `src/renderer/`; no platform-specific work.

## Anti-patterns — do not repeat

- **Don't introduce any AI-rewriting of the essay.** No "polish for LinkedIn" button, no "LinkedIn voice" version, no editable copy that the model has touched, no engagement-prediction scores ("predicted likes", "going viral"). The model's job is judgment (score + reason) and a single visual nudge (`picture_question`). The essay body is never modified by the model and never displayed to the user as a "LinkedIn-fied" version. If you find yourself adding a transform of the essay text, stop — that's the line the founder won't cross.
- **Don't make first-visit feel cold.** Today the user lands on a list of "Not read yet" rows with a "Read each one" button. The revamp's hero moment is the library already alive on arrival. If the user has essays and no cached scores, the page auto-runs the existing scoring pipeline on mount — without a button click — and renders the loading dots in place until each verdict lands. Don't add a "Welcome, click here to score" interstitial.
- **Don't push the user toward AI rewriting after a post.** The stuck point the founder named is "I posted one, now what" and the failure to fear is "they decide to feed their essay back into AI." Don't add an "improve next time" affordance, don't surface AI rewriting options on the post-action surface, don't add a coach beat. The next strongest fit floats up naturally as the library re-sorts.
- **Don't add notifications, daily prompts, top-pick beckoning, or progress meters.** The founder said no daily prompt. The library is composed by what they've written, not driven by an external pull.
- **Don't introduce new fonts, colors, button visuals, icon libraries, or a CSS framework.** Visual canon is `src/renderer/styles.css` + `src/renderer/design-tokens.css` + `src/renderer/tokens/rainbow-web.json`. Extend the existing `.linkedin-fit__*` classes; do not author parallel classes for the same concept.
- **Don't add team / multi-user / sharing features.** This is for the founder using their own essays.
- **Don't change the cache shape.** `tinker.linkedinFits.v1` keyed by essay id is the contract — `writing.js`, `sync.js`, and `linkedin-fit.js` all assume it. If you need to store the post-action state (e.g. "I already posted this one"), add a new key, don't mutate the verdict cache.
- **Don't ship the "Post to LinkedIn" deep link as if it always works.** LinkedIn's documented share URL (`https://www.linkedin.com/sharing/share-offsite/?url=`) only accepts a URL, not free text. The undocumented `https://www.linkedin.com/feed/?shareActive=true&text=...` parameter is honored intermittently on desktop web and not at all on mobile / in-app browsers. The build does a **best-effort prefill + guaranteed clipboard fallback**: open the compose URL with the essay text in `text=`, and at the same time copy the essay to the clipboard. When LinkedIn honors the prefill the composer is populated; when it doesn't, the user pastes. The button label swap (`Copied — paste in LinkedIn`) tells the user the paste path is always available either way. Don't ship just the URL prefill (it'll silently fail), and don't ship only the clipboard path either when a working prefill exists.

## What you're building, in one paragraph

A revamped LinkedIn writing review page that the founder opens daily — a permanent library of all their published essays scored 1–10 for how well they'd land on LinkedIn. On first arrival with essays present, the library auto-scores so the user lands in a populated workshop. New essays show up scored on return. The strongest fit carries a "Strongest pick" badge and a "Post to LinkedIn" action that copies the essay text and opens LinkedIn's compose feed — the essay posts unaltered, no AI rewriting between writing and posting. The page exists to make the user feel like a creator on LinkedIn rather than a consumer, by showing them they already have writing worth posting.

## Phase plan

**Single-phase build.** Target web/PWA only. The same `src/renderer/` is served by Electron desktop and Capacitor mobile shells; no platform-specific work, no native code path.

## Build sequence

1. **Verify the existing page renders today.** Run the dev server (`npm run dev` for desktop with DevTools, or `npx vercel dev` for the auth-gated web build). Sign in, open the LinkedIn fits page from the sidebar Account list (`#nav-linkedin`). Confirm: the page shows existing essays, the "Read each one" button scores them, the cache persists across reloads. If anything is broken before you start, fix that first — the revamp builds on a working base.

   **CHECKPOINT — stop and report.** Confirm the baseline page works on your local before touching code. If essays don't appear or scoring fails, surface the error before continuing.

2. **Auto-score on first arrival.** In `linkedin-fit.js`, inside `render()` (after `mount()` and after the essay list and rows are appended), add a single guarded auto-run: if the list has at least one essay AND at least one row's `state` is `idle` (i.e. no cached verdict), call the existing `checkAll()` function without user interaction. This reuses the existing concurrent-check loop (concurrency 3) and the existing per-row loading dots — no new UI primitive, just remove the click gate for the first-visit case.

   Guard against re-triggering: only auto-run if `viewEl.dataset.autoScored !== "true"`. Set the flag after the auto-run starts so a re-render during loading doesn't kick off a second pass. Clear the flag on full empty state (no essays).

   Returns with new essays since last visit: the same guard works, because new essays land as `idle` rows and the user's incoming render() call sees the same condition. (The `tinker:writing-saved` event re-renders, which sees fresh idle rows, which auto-scores.)

3. **Add the "Post to LinkedIn" affordance to fit rows.** In `refreshRow`, when `cached.fit` is true, append a small action to the existing `.linkedin-fit__row-actions` container alongside the "Read again" button. The action is a single button labeled exactly `Post to LinkedIn`. It must:

   - Copy the full essay body to the clipboard via `navigator.clipboard.writeText(essay.body)`. Fall back to a hidden `<textarea>` + `document.execCommand("copy")` if the async clipboard API throws (older Capacitor WebViews). The clipboard copy is the guaranteed path — it always works.
   - Open LinkedIn's composer in a new tab with a best-effort text prefill: `https://www.linkedin.com/feed/?shareActive=true&text=` + `encodeURIComponent(essay.body)`. Open with `window.open(url, "_blank", "noopener,noreferrer")`. When LinkedIn honors the `text=` parameter (desktop web, intermittently) the composer arrives populated; when it doesn't, the user pastes from the clipboard. Cap the prefilled text at a length LinkedIn's URL accepts (start with 3000 chars; truncate the URL-encoded value if needed). If you hit a URL length limit, drop the `text=` parameter entirely for that essay — the clipboard path still works.
   - After the open, swap the button label to `Copied — paste in LinkedIn` for 5 seconds, then revert. This is the "paste from clipboard" handoff cue; no toast, no modal. The label is honest whether LinkedIn prefilled the composer or not — paste is always the safety net.

   The two paths together mean: when LinkedIn's undocumented prefill works, the user sees a populated composer. When it doesn't, the user pastes one keystroke. The button never silently fails.

   **CHECKPOINT — stop and report.** Post one essay end to end. The button copies, LinkedIn's compose opens, you paste, the essay text arrives in the composer unaltered. Confirm with the founder that this is the intended posting flow before continuing.

4. **Style the row separators and the post action.** In `styles.css`, under the existing `.linkedin-fit__row` block, add a clear bottom border (use `--color-line` or the existing token used for separators in the sidebar) — the "Focused workshop" mood cue the founder picked is **clear row separators between essays**. Do not introduce a card visual (no shadow, no elevated background per row); the separator alone carries the rhythm. Remove the existing card-ish background from `.linkedin-fit__row` if it conflicts — the row should read as a list item with a horizontal rule beneath it, not a contained card.

   Style the `Post to LinkedIn` button: reuse the existing `.linkedin-fit__check` visual base (the same button class as "Read again"), but in a slightly quieter register (e.g. ghost variant of the accent color) so it doesn't overshadow the score chip or the reason. The score chip and the "Strongest pick" badge stay the strongest visual elements on the row — that's the content; the action is the follow-through.

5. **Add the cache key to the sync allowlist.** Open `src/renderer/sync.js`. Confirm `tinker.linkedinFits.v1` is in the synced-keys list. If not, add it next to `tinker.essays.v1` so a verdict scored on desktop shows up on phone without re-running the model.

6. **Walk the visible-string allowlist.** Before declaring done, open the rendered page in the browser and read every text node on screen. Each must be one of:

   - (a) verbatim from the founder's essay (the row title via `essaySnippet`, which uses `essay.title` or the first 8 words of `essay.body`),
   - (b) the model's verdict fields parsed from JSON (`reason`, `picture_question`, `strength`),
   - (c) a fixed UI string from this allowlist:

     - `Quiet review` (crumb)
     - `Which of these would do best as LinkedIn posts?` (page title)
     - `A short read through each essay, scored 1–10 on how well it would perform. The strongest float to the top. For each fit, a small question about a picture that might help readers land in it.` (sub)
     - `Read each one` (header button)
     - `No published essays yet. Finish a draft first.` (empty state)
     - `Not read yet.` (idle row meta)
     - `Read this one` / `Read again` / `Try again` (per-row primary button)
     - `Read →` (open-essay affordance on the row head)
     - `Could be a LinkedIn post.` (fit label)
     - `Better kept as an essay.` (miss label)
     - `Couldn't read this one.` (error label)
     - `Strongest pick` (badge)
     - `{N}/10` (score chip; N is the model's integer)
     - `Post to LinkedIn` (new — fit-row action)
     - `Copied — paste in LinkedIn` (new — 5-second post-click swap)

   Anything outside (a), (b), or (c) is a bug. Replace with the closest allowlisted phrase or, if a new string is genuinely needed, add it to the allowlist with a one-line justification in a code comment.

7. **Test the loop end to end.** From a logged-in state with at least three published essays: (a) open the page, see the library auto-score, (b) post the strongest one via the new action, (c) write a new essay in tinker, (d) return to the page, see the new essay score and re-sort, (e) confirm the previously-posted essay still appears (the page does not hide posted essays — there's no "posted" state in this build). If the loop works without the user being nudged toward AI rewriting at any step, ship it.

## Constraints (non-negotiable)

- **No AI rewriting of any kind, anywhere on the page.** The essay body is the post. The model produces a verdict (`fit`, `strength`, `reason`, `picture_subject`, `picture_question`) and nothing else; no transform of `essay.body` appears in the UI.
- **Not a one-shot scanner.** The page is a library the user lives in daily. First arrival populates automatically; returns show new essays scored.
- **Inside the existing renderer.** Files touched: `src/renderer/linkedin-fit.js`, `src/renderer/styles.css`, `src/renderer/sync.js` (allowlist only). The mount point (`<section id="linkedin-fit">`) and the sidebar trigger (`#nav-linkedin`) do not move. No new top-level HTML structure.
- **Visual canon is the existing tinker app.** `src/renderer/styles.css` + `src/renderer/design-tokens.css` + `src/renderer/tokens/rainbow-web.json`. No new fonts, no new color tokens, no CSS framework.
- **Clear row separators between essays.** That's the concrete mood cue. Not cards, not chips, not elevation — separators.
- **Cache contract preserved.** `tinker.linkedinFits.v1` keyed by essay id, verdict shape unchanged. Synced via `sync.js`.
- **No notifications, no daily prompts, no progress meters, no "what's next" beckoning.** The strongest fit floats up naturally; that's the only "what's next" the page offers.
- **The "Post to LinkedIn" action is honest.** Best-effort URL prefill via `?shareActive=true&text=` PLUS guaranteed clipboard copy. The button label swap tells the user the paste path is always available, so the affordance is honest whether LinkedIn honored the prefill or not.

## Open questions — ask the founder, don't invent

- **Does the `?shareActive=true&text=...` prefill work reliably enough to remove the clipboard path?** It's undocumented. As of this build, the assumption is it works on desktop web sometimes and not in mobile / in-app browsers. The clipboard path is the safety net. If you find that the prefill is now reliable across surfaces, the clipboard step can be demoted from "always" to "fallback only" — but verify across desktop Chrome, Safari, mobile Safari, and the Capacitor WebView before changing the behavior. The OAuth-based LinkedIn Share API would give a fully reliable prefilled compose; it requires LinkedIn app approval and is out of scope for v1, but belongs in a follow-up build if posting friction stays high.
- **Should posted essays get a visible "posted" state?** The founder didn't ask for one and the rule against beckoning suggests no. Confirm before adding any "you posted this on {date}" UI. For v1, the page does not track post events.
- **What happens on the empty state when the user has zero essays?** Today's copy is `No published essays yet. Finish a draft first.` — keep it; it's on the allowlist. If the founder wants a more inviting empty state (a one-line nudge toward `writing.js`), that's a separate ask.

If you must move forward without an answer, mark `[NEEDS INPUT]` in a code comment and pick a sensible default.

## Done when

- A user with at least one published essay opens the page and lands in a scored library — without clicking "Read each one" first.
- A user with a high-scoring essay can click `Post to LinkedIn`, paste into LinkedIn's compose, and the essay text arrives unaltered.
- A user writes a new essay in tinker, returns to the page, and sees the new essay scored without manual action.
- Every visible string on the rendered page traces to the allowlist, the essay body, or a parsed verdict field.
- No affordance on the page invites or implies AI rewriting of the essay text.
- The `tinker.linkedinFits.v1` cache is synced across devices.
